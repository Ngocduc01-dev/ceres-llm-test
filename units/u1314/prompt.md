# 1. NHIỆM VỤ

Bạn là kỹ sư kiểm thử phần mềm. Hãy thiết kế bộ test cho **một hàm C++** (gọi là **unit**) ở mục 3 theo phương pháp **kiểm thử luồng điều khiển (CFT)**, sao cho đạt **độ phủ nhánh C2**, rồi viết bộ test đó thành **một file GoogleTest** (thư viện viết unit test cho C++) chạy được.

- Dự án: thư viện **Ceres Solver 2.2.0**, viết bằng C++17.
- Dự án **không có tài liệu mô tả kết quả đúng**, nên **không cần kiểm tra kết quả trả về**. Mục tiêu chỉ là gọi hàm sao cho chương trình **đi qua đủ các nhánh**.

# 2. KHÁI NIỆM CẦN DÙNG

- **CFG (đồ thị luồng điều khiển):** sơ đồ các bước của hàm. Mỗi **node** là một đoạn lệnh chạy liền nhau hoặc một chỗ rẽ nhánh; mũi tên nối các node theo thứ tự chạy.
- **Điểm rẽ nhánh:** chỗ chương trình chọn đường đi theo một điều kiện: `if`, `else if`, vòng `for` / `while`, `switch`, `?:`. Mỗi điểm rẽ nhánh có **2 nhánh**: điều kiện **đúng** và điều kiện **sai** (`switch` có 1 nhánh cho mỗi `case`).
- **Độ phủ C2 (phủ nhánh):** mọi nhánh của mọi điểm rẽ nhánh đều được chạy qua ít nhất 1 lần.
  **C2 = số nhánh đã chạy qua / tổng số nhánh × 100%.**
  (C2 chặt hơn C1 – chỉ yêu cầu mỗi câu lệnh chạy ít nhất 1 lần. Ví dụ `if (x > 0) y = 1;`: chỉ cần x > 0 là đạt C1, nhưng C2 cần thêm 1 test với x ≤ 0.)
  Điều kiện ghép như `a && b`, `a || b` được tính là **một** điểm rẽ nhánh.
- **Test path (đường kiểm thử):** một đường đi trên CFG, từ `START` tới `END`, ghi rõ ở mỗi điểm rẽ nhánh đi theo nhánh nào.
- **Điều kiện của đường đi:** các điều kiện phải đúng/sai dọc theo một test path. Dữ liệu đầu vào của test phải thoả các điều kiện này.
- **Nhánh không thể đi tới:** nhánh mà không có dữ liệu nào làm chương trình đi vào (ví dụ điều kiện mâu thuẫn). Ghi rõ lý do, vẫn tính vào tổng số nhánh.
- **Vòng lặp:**
  - Có giới hạn số lần lặp n (ví dụ `for (i = 0; i < size; ...)`): test với **0, 1, 2, một số ở giữa, n−1, n** lần lặp; thêm **n+1** nếu làm được.
  - Không có giới hạn (lặp đến khi thoả một điều kiện, ví dụ `while (!done)`): test với **0, 1, 2** lần lặp và **mỗi cách thoát khỏi vòng lặp** (`break`, `return`, điều kiện sai) ít nhất 1 lần.
  - Số lần lặp nào không làm được thì ghi lý do.
- **`CHECK(...)`:** lệnh kiểm tra của thư viện glog mà Ceres dùng. Nếu điều kiện sai, chương trình **dừng ngay**. **Không** cố tình làm `CHECK` sai; ghi nhánh đó là "không test (làm chương trình dừng)".

# 3. ĐẦU VÀO

## 3.1. Unit cần test

- Hàm: `FindMinimumOnTrustRegionBoundary(Vector2d * minimum) const`, trả về `bool`
- Loại: method (hàm thành viên của class)
- Thuộc class: `ceres::internal::DoglegStrategy`
- Vị trí: `internal/ceres/dogleg_strategy.cc`, dòng 472–514

Mã nguồn (số ở đầu dòng là số dòng trong file):
```cpp
472 | bool DoglegStrategy::FindMinimumOnTrustRegionBoundary(Vector2d* minimum) const {
473 |   CHECK(minimum != nullptr);
474 | 
475 |   // Return (0, 0) in all error cases.
476 |   minimum->setZero();
477 | 
478 |   // Create the fourth-degree polynomial that is a necessary condition for
479 |   // optimality.
480 |   const Vector polynomial = MakePolynomialForBoundaryConstrainedProblem();
481 | 
482 |   // Find the real parts y_i of its roots (not only the real roots).
483 |   Vector roots_real;
484 |   if (!FindPolynomialRoots(polynomial, &roots_real, nullptr)) {
485 |     // Failed to find the roots of the polynomial, i.e. the candidate
486 |     // solutions of the constrained problem. Report this back to the caller.
487 |     return false;
488 |   }
489 | 
490 |   // For each root y, compute B x(y) and check for feasibility.
491 |   // Notice that there should always be four roots, as the leading term of
492 |   // the polynomial is r^2 and therefore non-zero. However, as some roots
493 |   // may be complex, the real parts are not necessarily unique.
494 |   double minimum_value = std::numeric_limits<double>::max();
495 |   bool valid_root_found = false;
496 |   for (int i = 0; i < roots_real.size(); ++i) {
497 |     const Vector2d x_i = ComputeSubspaceStepFromRoot(roots_real(i));
498 | 
499 |     // Not all roots correspond to points on the trust region boundary.
500 |     // There are at most four candidate solutions. As we are interested
501 |     // in the minimum, it is safe to consider all of them after projecting
502 |     // them onto the trust region boundary.
503 |     if (x_i.norm() > 0) {
504 |       const double f_i = EvaluateSubspaceModel((radius_ / x_i.norm()) * x_i);
505 |       valid_root_found = true;
506 |       if (f_i < minimum_value) {
507 |         minimum_value = f_i;
508 |         *minimum = x_i;
509 |       }
510 |     }
511 |   }
512 | 
513 |   return valid_root_found;
514 | }
```

## 3.2. CFG của unit

CFG đã được dựng sẵn bằng công cụ phân tích mã nguồn:
```
Số điểm rẽ nhánh: 4 (và 1 lệnh CHECK)

START → 1
1   CHECK(minimum != nullptr)                                      đúng → 2   sai → DỪNG
2   minimum->setZero()
    MakePolynomialForBoundaryConstrainedProblem()                  → 3
3   if (!FindPolynomialRoots(polynomial, &roots_real, nullptr))    đúng → 4   sai → 5
4   return false                                                   → END
5   double minimum_value = std::numeric_limits<double>::max()
    bool valid_root_found = false
    int i = 0                                                      → 6
6   vòng for, điều kiện: i < roots_real.size()                     đúng → 7   sai → 13
7   ComputeSubspaceStepFromRoot(roots_real(i))                     → 8
8   if (x_i.norm() > 0)                                            đúng → 9   sai → 12
9   const double f_i = EvaluateSubspaceModel((radius_ / x_i.norm()) * x_i)
    valid_root_found = true                                        → 10
10  if (f_i < minimum_value)                                       đúng → 11   sai → 12
11  minimum_value = f_i
    *minimum = x_i                                                 → 12
12  ++i                                                            → 6
13  return valid_root_found                                        → END
```

**Cách đọc:** dòng đầu cho biết hàm có bao nhiêu điểm rẽ nhánh. Mỗi dòng sau đó là **một node**: số node, nội dung (câu lệnh hoặc điều kiện), rồi mũi tên tới node tiếp theo. Dòng "Ghi chú" (nếu có) cho biết unit là template và CFG được dựng với kiểu dữ liệu cụ thể nào.
- Node có điều kiện ghi `đúng → x   sai → y`: điều kiện đúng thì đi tới node x, sai thì đi tới node y.
- `START`: bắt đầu hàm · `END`: kết thúc hàm · `DỪNG`: chương trình dừng do `CHECK` sai.
- Nếu thấy CFG không khớp với mã nguồn, **tin mã nguồn** và ghi chú lại.
- Khi trả lời, gọi các node bằng **đúng số node này**.

## 3.3. Cách gọi unit trong file test

Các dòng `#include` được dùng:
```cpp
#include "gtest/gtest.h"
#include "ceres/dogleg_strategy.h"
```

- Method này là `private` (bên ngoài class không gọi được). Thêm 2 dòng `#define private public` và `#define protected public` **sau** `#include "gtest/gtest.h"` và **trước** các `#include` của Ceres.
- Đây là method của class `ceres::internal::DoglegStrategy`: tạo một object của class rồi gọi method trên object đó.

# 4. YÊU CẦU ĐỐI VỚI BỘ TEST

1. Mỗi nhánh (đúng và sai) của mỗi điểm rẽ nhánh có **ít nhất 1 test** đi qua.
2. Mỗi vòng lặp được test với số lần lặp như mục 2.
3. Mỗi test ứng với **một test path**, ghi rõ các nhánh nó đi qua (ví dụ `node 2: đúng, node 4: sai`).
4. Dùng **ít test nhất** có thể: một test nên đi qua nhiều nhánh chưa được phủ.
5. **Dữ liệu đầu vào:** từ điều kiện của đường đi, xác định **khoảng giá trị** hợp lệ cho từng đầu vào (ví dụ `n` từ 1 đến 5), rồi **chọn ngẫu nhiên một giá trị** trong khoảng đó. Nếu dùng hàm sinh số ngẫu nhiên trong code thì **cố định giá trị khởi tạo (seed)** để mỗi lần chạy ra cùng một giá trị. Mảng, ma trận nhỏ (tối đa 5 phần tử). Không dùng file, mạng, đa luồng.
6. **Không** kiểm tra kết quả trả về (không có kết quả đúng để so).

# 5. CÁC BƯỚC THỰC HIỆN

1. Đọc mã nguồn và CFG của unit.
2. Liệt kê các điểm rẽ nhánh và các nhánh cần phủ.
3. Chọn các test path sao cho phủ hết các nhánh (trừ nhánh không thể đi tới và nhánh `CHECK` sai).
4. Với mỗi test path: viết điều kiện của đường đi → khoảng giá trị đầu vào → chọn giá trị ngẫu nhiên trong khoảng.
5. Viết code GoogleTest: mỗi test chuẩn bị dữ liệu rồi gọi unit **một lần**.
6. Kiểm tra lại: mọi nhánh đã có test chưa, code có dùng đúng tên hàm và `#include` ở mục 3.3 không.

# 6. KẾT QUẢ CẦN TRẢ VỀ

**A. Test paths**

| Path | Đường đi (theo số node) | Các nhánh đi qua |
|---|---|---|
| P1 | START → 1 → 2 → … → END | node 1: đúng, node 2: sai |

**B. Bộ test case**

| Test | Path | Khoảng giá trị đầu vào | Giá trị đã chọn |
|---|---|---|---|
| TC1 | P1 | … | … |

**C. Nhánh không test** (nếu có): nhánh nào, vì sao. Kèm 1 dòng: `C2 dự kiến = <số nhánh có test> / <tổng số nhánh>` (dự kiến, chưa chạy thật).

**D. File test:** đúng **một** khối code C++, dòng đầu là `// FILE: u1314_test.cc`. Mỗi test case ở bảng B là một `TEST(...)`, ngay trên đó có 1 dòng comment ghi path.
